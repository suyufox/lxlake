## M0 地基

交付一个空窗口，事件齐全，帧率稳定。**不含任何渲染内容。**

- workspace 与主库模块骨架（`core` / `runtime` / `platform` / `lxlake-macros`）
- `platform/windows` 后端：窗口、resize、DPI、close
- `runtime`：`App`、帧循环、`#[lxlake::entry]` 宏
- **外部事件源 / pump 钩子的接口**：允许帧边界之外被唤醒。M0 只交接口不交实现

验收：`cargo run -p lxlake-demo` 出一个空窗口，60fps 稳定，缩放与 DPI 变化正确响应。

**已交付**：`core` / `runtime` / `platform` / `render` 骨架就位，`#[lxlake::entry]` 可用。demo 实测稳定 60fps，resize 响应正确；`cargo build -p lxlake-editor` 的依赖图里 wgpu / naga 出现 **0 次**。外部事件源 / pump 交的是**接口 + 调度**（源声明截止时间、运行时按最早者设 `WaitUntil`；跨线程唤醒走 `EventLoopProxy`），不含任何 wry / CEF 实现——webview 线的第一件事就是拿它核对 ~10ms 泵的语义。

## M1 空岛只读

[架构](architecture.md) 的「世界与区块」。

按包验证（**不跑 `--workspace`**）已通过：`cargo test -p lxlake --features render` 39 项全绿
（含 render 的布局对照、光投影稳定性、图集扰动值域），`cargo clippy -p lxlake --all-features --all-targets`
与 demo / editor 的 clippy、`cargo fmt --check` 均无告警；`cargo build -p lxlake-editor` 的依赖图里
wgpu / naga / bytemuck 出现 **0 次**（bytemuck 随 `render` 特性分档）。剩下的是**实机看一眼**：
窗口里的画面、帧率与流式进度（标题栏每秒刷新）。

### 实机第一跑踩到的三件事

首次实机运行连破三个问题，都值得记下来，因为它们各自暴露了一类以后会反复遇到的坑：

1. **图形后端在 Windows 上只开 D3D12**。这台机器的 Intel Gen9 Vulkan 驱动一进
   `adapter.request_device` 就 AV 崩掉进程（`0xc0000005`，无任何输出）。多开一个后端换不来任何
   东西，只会换来「在谁的机器上崩、为什么崩」这种排查成本——所以 `render` 里硬编码
   `Backends::DX12`。另外 `InstanceDescriptor::new_without_display_handle()` **不读
   `WGPU_BACKEND` 环境变量**，靠环境变量换后端是无效的。
2. **同一 render pass 内，一张纹理不能既是深度附件又是着色器资源**。阴影 pass 里阴影贴图正被
   当深度附件写，就不能同时在绑定里当资源读——即使那条绑定在 layout 里只声明了片元可见性。
   修法是绑定拆两组：0 号组只有全局 uniform（阴影 pass 也要光矩阵），1 号组是图集与阴影贴图
   （只给主管线）。
3. **`Queue::write_buffer` 要求缓冲带 `COPY_DST`**。`create_buffer` 的调用方只声明它**用**这份
   缓冲干什么（顶点 / 索引），灌数据那一侧的用途由 `create_buffer` 统一补上。

### 做

- **世界**：体素区块 + 方块注册表 + 噪声/3D 密度场生成的浮岛，固定种子
- **渲染**：greedy meshing + 纹理图集 + 方向光阴影 + 雾 + tone mapping
- **流式**：视距内区块异步生成与网格化，出视距卸载
- **输入**：只有自由飞行相机（无碰撞、无重力）

### 不做

碰撞、重力、行走、破坏/放置、HUD、存档、webview、脚本插件。

### 验收

1. 飞一圈，帧时间稳定不掉
2. 区块异步生成不阻塞主线程
3. 关掉 `render` 后 `cargo build -p lxlake-editor` **完全不编译 wgpu**

第 3 条是对「框架主线不依赖渲染」这条架构约束的第一次真实验证，比画面本身更重要。

### 视觉标准：像素质感纹理 + 现代光照

这是「偏写实、动漫风」路线的第一个落点，也是 NPR 叠加层的试验场。三条具体口径：

- 纹理用像素风图集，采样必须是 **point 而非 linear**——像素质感的关键在这里，漏掉就变成模糊的方块
- 光照走 PBR 主光路，先只吃 albedo + 法线；金属度/粗糙度贴图与级联阴影延后
- 后处理：tone mapping + 轻雾

NPR 部分在 M1 只留一个 ramp 光照 / 边缘光的开关，验证「能叠上去」，不追求好看。复刻原版方块游戏光照被否决——快，但对渲染主线的能力几乎没有验证价值。

## M2 交互

**代码已全部落位，按包验证已通过**：`world::collision`（AABB 扫掠，沿轴分离）、`world::raycast`
（DDA 步进射线，返回命中方块 + 命中面）、`core::command` 与 `core::input`（意图 / 命令 / 键位表）、
`world` 的 copy-on-write 写方块与流式槽位脏状态（标脏 → 重算 → 覆盖上传）、`camera` 的
转向 / 位移拆分，以及 `lxlake-demo` 的接线（左键破坏 / 右键放置、位移先过一遍碰撞夹紧、
`HeldKeys` 收成键位表）。命令序列每帧打到 stdout（验收第 4 条）。

验证（**不跑 `--workspace`**）：`cargo test -p lxlake` 69 项、`--features render` 78 项全绿；
`lxlake` / `lxlake-macros` / `lxlake-demo` / `lxlake-editor` 的 `clippy --all-targets -D warnings`
与 `cargo fmt --check` 无告警；`cargo build -p lxlake-editor` 的依赖图里 wgpu / naga / bytemuck
仍是 **0 次**（验收第 5 条）。剩下的是**实机看一眼**：对着地形点左键 / 右键，画面下一帧更新、
帧时间不掉。

一行摘要见上面的表：体素碰撞 + 射线破坏/放置 + 命令流。要逼出的三样是**命令契约**、**世界可变性**、
**输入与模拟的分界**，下面把它们各自落成具体设计。

### 做

- **世界可变性**：改方块 → 换新快照 → 标脏 → 重新网格化（含边界邻块）
- **射线投射**：体素 DDA 射线，从相机眼位沿朝向命中方块，返回命中方块坐标 + 命中面法线
- **碰撞**：AABB 扫掠查询 + 自由飞行的**夹紧**（撞墙就停），不引重力 / 走路 / 跳跃
- **命令**：可序列化的数据枚举 + 一处执行器；一帧的命令收集成序列，在帧边界按序应用
- **输入与模拟分界**：平台事件 → 键位表（按键 → 意图）→ 模拟（射线 / 命令生成）→ 命令 → 世界
- **demo 接线**：左键破坏、右键放置，画面下一帧就更新

### 不做

重力、走路、跳跃、台阶、破坏动画与粒子、方块掉落物、撤销（undo）、联机同步、自定义键位 UI。

### 验收

1. 对着地形破坏与放置都生效，画面**下一帧**就更新，帧时间不掉
2. **在区块边界上改方块，接缝正确**——没有洞、没有该藏的面露出来
3. 撞墙就停，穿不过实心方块；不加任何重力仍能自由飞
4. 命令可序列化：能打印出「这一帧产生的命令序列」，为 M4 存档与将来的联机留口
5. 关掉 `render` 后 editor 仍编译且依赖图里没有 wgpu（延续 M1 第 3 条）

### 世界可变性：从「不可变快照」到「可替换快照」

M1 的前提是「区块生成后不再改」，于是 `World` 只给 `insert` / `remove`，网格化吃 `Arc<Chunk>` 快照，
工作线程永远读不可变数据、也就不需要锁。M2 要打破前半个前提，但**不能打破后半个**——所以走
copy-on-write：

- 区块仍是 `Arc<Chunk>`；改动时在**主线程** clone 出新 `Chunk`（32³ = 32KB）替换旧的那份。正在跑
  的网格化作业手里还握着旧快照，它会安全地跑完，只是结果作废（脏标记会再排一次）
- 代价：改一个方块复制 32KB。放在「玩家点一下」这个频率上可以忽略；将来要高频批量改（爆炸、
  流体），再引入 16³ 子区块细分——**M2 不做**
- 改动点落在**区块边界 1 格内**时，相邻区块也要标脏：那一面是否可见变了，只重算自己会在接缝处
  留下错面。这是验收第 2 条要盯的东西

### 重新网格化：给流式槽位加一条回头的路

现在 `Streamer` 是单向流：申请 → 生成 → 网格化 → 收割 → 上传，**没有回头的路**。M2 给槽位加「脏」
状态：区块被改 → 标脏 → 下一帧重新提交网格化作业（吃它自己与邻居的当前快照）→ 收割后走
`Renderer::upload` 覆盖上传（`upload` 对已存在的 pos 本来就是 insert 覆盖，天然支持）。

### 射线投射：DDA 步进，不用采样

起点 = 相机眼位，方向 = 相机朝向，用 DDA（Amanatides & Woo）严格按网格单元步进，返回命中方块坐标
与命中面法线。**必须步进，不能沿射线采样**——采样会漏掉斜面上的方块与角落。射程给上限（先取 8
方块，与「手够得到的距离」同一量级）。实心判定走 `World::block_at`，缺失区块按空气。

放置位置 = 命中方块坐标 + 命中面法线；破坏位置 = 命中方块坐标本身。法线是这里唯一能区分「点的是
哪一面」的信息，所以射线必须把面一起返回。

### 碰撞：只查询 + 夹紧

给一个 AABB 与一个位移，返回**允许的位移**：沿轴分离（先解 x、再 y、再 z），这样斜着撞角不会穿过去。
相机保持自由飞行，只是把位移先过一遍夹紧。

不含重力、地面判定、跳跃、台阶、站立 / 蹲下——那些属于「玩家控制器」，排在 M2 之后。M2 只回答
「这一帧我能走到哪」。

### 输入与模拟的分界：意图与命令分两层

链路：平台事件 → 键位表 → **意图** → 模拟层 → **命令** → 世界 → 重网格化。

- **意图**（`挖掉` / `放一个`）与设备无关，也不知道世界坐标
- **命令**（`Break { pos }` / `Place { pos, block }`）已经解析出目标坐标，是可序列化的数据
- 分开的理由：意图不必来自鼠标——将来 UI、脚本、回放都能产生意图；而命令可以录制、回放、网络传输。
  两者混成一层，M4 存档与联机就得回头拆

命令的收集与排空：一帧内产生的命令进一个序列，在**帧边界、模拟之前**按序应用。这既是「命令流」
的落点，也是 M4 存档与将来联机的接入点。

### 键位表：M2 做数据化，不做可配置

自定义快捷键分两半，落点不同：

- **M2 只做数据化**。键位表做成**数据**（一张 `按键 → 意图` 的映射），不是散在 `match` 里的硬编码
  ——M1 的 demo 里那份 `HeldKeys` 就是硬编码，M2 要把它收成表。命令与键位表都进契约层，于是
  **第三方应用接入时能声明自己的默认键位**
- **用户覆盖与 UI 延后**。终端用户运行时改键需要两样东西，都不在 M2：改键界面要等 M3 自绘 HUD 才有
  地方放，键位的持久化属于配置读写（与 M4 存档同源）

契约层因此要预留**两层**结构：**应用声明的默认键位 + 用户配置的覆盖**，覆盖优先。M2 只落前者与
「可覆盖」的形状，覆盖本身留到 M3/M4。

## M3 与覆盖层（当前目标）

M3 的 HUD 用**自绘 UI**，覆盖层（wry）在这里第一次接上，验证与自绘 UI 的 z 序和输入穿透关系。

**切 1–3 已落位**：`core::widget`（UiId / 九宫格锚定 / Widget，含 overlay 标记）、`core::event` 的

**切 4 也已落位**：`capability::webview` 的接口层（`OverlaySpec` / `WebViewHandle` / 能力查询，常编译）

按包验证（**不跑 `--workspace`**）：`cargo test -p lxlake` 155 项、`--features render` 170 项、
`--features webview-wry` 155 项、`cargo test -p lxlake-demo` 5 项全绿；`clippy --all-targets -D warnings`
与 `cargo fmt --all --check` 无告警；`cargo build -p lxlake-editor` 的依赖图里 wgpu / naga / bytemuck
仍是 **0 次**（排版只用普通依赖 `ab_glyph`，不受 `render` 门控；wry 同样不在 editor 的图里）。剩下的是
**实机看一眼** HUD 与覆盖层：覆盖层在最上（Tab 面板也盖不住它）、矩形内点击不挖方块也不转视角、
resize 与 DPI 变化后仍锚在右下角。

同一轮还顺手做了**框架主线的重构**：`Builder` 装配面、窗口身份（标签取窗与多窗口）、统一路径层、
日志与异步运行时、命令总线，并为 android 铺好入口（接入已落地、类型检查已过，打包与真机在后）。
它不被里程碑的交付项绑定，但把堆在 demo `main.rs` 里的接线收进了运行时——形状见[架构](architecture.md)
的「应用装配」。M3 的**代码**因此全部落位，只剩实机验收。

### 做

- **契约**：UiId / 九宫格锚定 / Widget——自绘与覆盖层**共用一份**摆位数据
- **布局与命中测试**：锚定摆位，z 序按「覆盖层整组优先、同组内后加者胜」
- **文本**：字体由应用提供（`data/` 资产），排版只出方片
- **渲染**：独立 UI 图集 + 正交方片管线（alpha 混合、不写深度），与主 pass 共用同一个 encoder
- **输入闸口**：UI 抢走控制权时，事件不进 `IntentState`
- **demo HUD**：fps / GPU 区块 / 世界区块 / 相机坐标 + 准星 + Tab 调试面板

### 不做

可交互控件（按钮 / 输入框 / 滚动）、UI 动画与过渡、富文本与自动换行、IME、无障碍、主题系统、
改键界面（仍然留到 M4 与配置读写同源）。

### 验收

1. 左上角面板显示实时 fps / 区块数 / 相机坐标，字形清晰（高 DPI 下不糊）
2. 准星恒定在屏幕正中，窗口缩放后仍贴着中心
3. 面板打开时键盘与视角归面板；**准星不吞点击**——面板没开时对着中心破坏 / 放置照旧生效
4. 关掉 `render` 后 editor 仍编译，且依赖图里没有 wgpu（延续 M1 / M2）

### 出图形式只有方片

UI 的一条管线画一切：底色、准星、字形都是同一个 quad 顶点格式（NDC 位置 + uv + sRGB 颜色）。字形
只是「uv 指向 UI 图集里的某一格」，而实心方片一律指向 0 号格那个不透明纹素——**用常量采样代替
分支**，因此不需要两条管线、两种顶点格式。代价是没有圆角与描边，收益是形状变化全留在 CPU 侧的
矩形里。

颜色有个容易踩的点：UI 的颜色是 sRGB，而混合发生在 sRGB 表面目标的**线性**空间里，所以片元着色器
必须自己把 sRGB 转成线性，否则半透明底色会偏亮。

### 字形按物理分辨率光栅化

清晰度的关键在这一条：字形按 `字号 × DPI` 光栅化，再除回逻辑像素交出矩形。若按逻辑分辨率光栅化，
高 DPI 屏上的字会被系统放大糊掉。代价是同一个字在不同 DPI 下是两份位图，所以图集键里带的是
**物理尺寸**。字形位图**增量**上传（`take_new_glyphs`）——它们是这几刀里唯一的「大块 CPU 数据」，
每帧重传整个图集纯属浪费。

UI 图集与方块图集**是两份**：格尺寸、纹理格式（`R8Unorm`）、采样方式（Linear；方块那套是
Nearest）、生命周期都不同，合并没有任何好处。

UI 管线**不需要 uniform**：方片是逻辑像素，NDC 换算只用逻辑视口尺寸（物理 = 逻辑 × DPI，换算时
DPI 约掉），所以 DPI 只影响字形光栅化。

### 输入闸口：准星为什么不吞点击

准星是屏幕正中一个 10×10 的 Widget，若它参与命中测试，每一次「对着中心挖方块」的点击都会被自己的
准星吃掉。规则因此分两条：**连续控制**（键盘轴值、视角转向）只看「面板开着吗」——面板是模态的；
**指针点击**则要求「面板开着 **且** 指针落在某个 Widget 上」。面板没开时光标是锁住的，不存在
「指针在哪」这回事，所以准星永远抢不走点击。

面板开着时正中那一下落在面板上而不是准星上，靠的是**加入顺序**：帮助面板摆在正中且后加（后加者
在上层），命中测试先撞到它。这条顺序有单测钉住（`the_open_panel_covers_the_crosshair_at_the_center`）。

开关面板时一并清空意图状态：面板期间按键抬起事件被闸口挡在外面，不清就会留下「一直按着 W」的
轴向，关掉面板后相机自己往前飞。

## webview 双线（独立于空岛）

webview 不被空岛进度绑定，另起一条线。它与空岛的**交汇点**是 M0 的 pump 钩子接口（wry 那一半后来
实测用不上，见下）：

1. M0 交付接口（外部事件源注册 + 帧边界外唤醒），不含 wry 实现
2. **已核对**：拿这个接口核对能否满足 wry / CEF 约 10ms 泵的语义——结论是**够用，`runtime` 不用改**（见下）
3. 之后才是：wry 覆盖层（**已落位**，仅 Windows）→ CEF 纹理层

### 钩子核对结论（已做）

`runtime` 的机制是：源用 `next_deadline()` 声明下一次必须被泵的**绝对**时间点 → 运行时把所有源的
最早者与下一帧时间取小，据此设 `ControlFlow::WaitUntil` → 醒来后 `about_to_wait` **先泵源、再出帧**；
从别的线程被 `Wakeup` 叫醒时则补一帧并顺带泵一遍源。于是「比帧更细的泵」成立：帧是 16.6ms 时，
源仍会按自己声明的 ~10ms 被泵到。**wry 与 CEF 都能直接接，不需要改动运行时主干。**

**实测修正（wry 接上后）**：**wry 0.57 没有 `pump` 接口**——覆盖层的活跑在宿主消息循环里，`winit`
的事件循环本身就是它的泵。所以**覆盖层这一半用不上外部事件源钩子**，钩子的受力点在 CEF：离屏渲染
要按自己的节奏泵 message loop，那套 `EventSource` 语义到那时才真正被检验。

两条留给实现者的契约（写进了 `runtime/pump.rs` 的文档，且已被单测钉住）：

- **泵是「至少」这么勤**：任何**一个**源到期，运行时会泵掉**全部**源。所以 `pump` 必须廉价、
  且能承受超频调用。
- **原生窗口不在 `PumpContext` 里**：wry / CEF 要的父窗口句柄由源在构造时自己拿着
  （`AppContext::main_window()` 给的是 `Arc<dyn WindowHandle>`），运行时不必每泵一次塞一次。
  接口因此始终不认识窗口，也就不必为它加窗口类型的门。

CEF 需要先自建 vcpkg overlay port（下载官方预编译分发 + 校验和 + 暴露 CMake 包，不 fork、不加子模块），并核对沙箱接入步骤。`cef-ffmpeg` 完全体强制 GPL，单独特性、单独发行物。

### 开工时机

「2D 覆盖层」在这个项目里分两种，开工点不同：

| 东西                       | 开工点                          | 说明                                                                                                   |
| -------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **自绘 UI**（HUD / 2D 层） | M3                              | 「自绘 UI 第一刀」，不依赖 webview 线                                                                  |
| **wry 原生覆盖层**         | **M3 已落位**（仅 Windows）     | 与自绘 UI 同时出现，要的就是验证两者的 z 序与输入穿透关系；wry 0.57 无 `pump` 接口，宿主消息循环即其泵 |
| **CEF 纹理层**             | wry 之后，最晚                  | 先有 vcpkg overlay port；`cef-ffmpeg` 另立发行物                                                       |
| **pump 语义核对**（前置）  | **不绑里程碑，M2 之后随时可做** | 拿 M0 的钩子核对 wry / CEF 约 10ms 泵；不够就先改 `runtime`                                            |

也就是说：覆盖层本身在 M3 开工，但**它前面那道工序（拿 pump 钩子核对语义）可以提前**，而且提前做代价
最低——等 wry 真接上再发现钩子语义不够，改的就是运行时主干了。

## 资产管线（独立于空岛）

发行物的 `data/` 目录（形状见[架构](architecture.md)的发行物形状）要有东西可放，就得先有资产管线。
**当前是零**：M1 的纹理图集是程序化生成的、几何由噪声密度场算出，全项目没有一个外部资产文件。

这条线要覆盖的资产类别：

- **模型**：引擎所需的所有模型文件（角色、道具、场景物件）。**基准格式定为 glTF 2.0（`.glb`）**
  ——开放标准、Blender 原生导出、PBR 材质与骨骼动画齐备、Rust 侧读取实现成熟，不必自造格式。它是
  **作者格式**；将来资产量大到读取成为瓶颈，再由导入器烘焙成运行时紧凑格式，游戏侧代码不动
- **本地化**：文案表与语言回退
- **纹理 / 着色器**：从程序化过渡到外部文件，图集与 `.wgsl` 都要能被替换

**体素管「世界」，模型管「世界里的实体」**：地形与方块是体素（greedy meshing 那套，不会被模型替代），
角色、道具、掉落物、2D 精灵这类才是模型文件。两者共用顶点布局与材质绑定，但走不同的上传路径。

这条线与空岛进度不绑定，只被 M2 之后的里程碑（要真放进去一个模型时）拉动。

## 里程碑之后

联机（主单机，但要服务器数据同步能力）、编辑器、移动端端到端、脚本插件、以及 `media` / `update` 等横切能力。这些都不在 M0–M4 排期内。

## 依赖的取舍

引擎内部一律 `rlib` 静态链接（全量单态化 + 跨 crate LTO，性能最优），只留一条窄的、可版本化的 C ABI 边界给插件。`dylib` 不用于分发——它不打包 std、须随附与编译器精确匹配的 `std-<hash>`，且跨边界完全无法 LTO。

进度只在本页改。
